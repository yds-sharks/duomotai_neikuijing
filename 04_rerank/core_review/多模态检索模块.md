## 2. 模块定位

这是实际的多模态检索模块，负责：

- 构建文本向量库
- 构建图片向量库
- 用统一接口做文本检索或图片检索
- 支持过滤、去重、离线批量跑检索

输入可以是：

- 查询文本
- 查询图片路径

输出是：

- 检索命中结果
- 命中分数
- 命中文本/图片关联信息
- 过滤条件与检索参数

## 6.2 上游文本数据从哪里来

当前主库里的文本数据不是直接从 PDF 进向量库，而是先进入统一 SQLite 主库。

这条链是：

- 上游 labeled 文本库：
  - `/mnt/data_1/yds/多模态/data_house/origin_data/blocks_classification/text_database_stage3_filtered_labeled.db`
- 被 [`build_multimodal_samples.py`](/mnt/data_1/yds/多模态/data_house/build_multimodal_samples.py) 读取
- 转成统一主库：
  - [`multimodal_samples.db`](/mnt/data_1/yds/多模态/data_house/multimodal_samples.db)
- 再由 [`build_multimodal_milvus.py`](/mnt/data_1/yds/多模态/retrieval/多模态/build_multimodal_milvus.py) 构建出：
  - `text_vector_index`

这意味着：

- 如果你要新增文本向量，通常不应该只改 Milvus
- 更合理的是先把新增文本补进 `multimodal_samples.db`
- 然后再重新构建或改造成增量写入文本 collection

## 6.3 当前脚本的一个关键限制

这点对你下一步非常重要：

- 当前 [`build_multimodal_milvus.py`](/mnt/data_1/yds/多模态/retrieval/多模态/build_multimodal_milvus.py) 默认不是“增量追加文本向量”
- 它对文本库当前采用的是“重建 collection”的策略

原因是主流程里只要不传 `--skip-text`，就会执行：

- `recreate_collection(TEXT_COLLECTION_NAME, build_text_schema())`

而 `recreate_collection(...)` 会：

- 如果 collection 已存在，则先 `drop`
- 然后重新创建 `text_vector_index`

所以按当前代码直接跑文本构建，相当于：

- 删除旧的 `text_vector_index`
- 从 `multimodal_samples.db` 全量重建文本向量库

这对“重新全量建库”是安全清晰的，
但对“在当前文本向量库基础上新增少量向量”来说，不属于真正的增量方案。

## 6.5 新增的文本向量追加脚本

为了基于现有 `text_vector_index` 做追加，而不是全量重建，我新增了一份脚本：

- [`append_text_vector_index_from_jsonl.py`](/mnt/data_1/yds/多模态/核心代码梳理/append_text_vector_index_from_jsonl.py)

这份脚本的设计目标是：

- 读取新增 `JSONL`
- 先做格式校验与标准化
- 确认能映射到 `text_vector_index` 所需字段
- 检查 Milvus 中已存在的 `id`
- 只对新记录生成 `BGE-M3` 向量并追加写入

安全策略：

- 默认只做校验，不写库
- 必须显式传 `--append` 才会真的入库
- 已存在的 `id` 默认跳过

## 7. 检索接口含义

请求里的关键字段：

- `Q`
  - 文本库时表示查询文本
  - 图片库时表示查询图片路径
- `k`
  - 返回前 `k` 条结果
- `level1`
  - 一级过滤，对应 `body_site_main`
- `level2`
  - 二级过滤，对应 `knowledge_type_main`
- `retrieval_db`
  - `text` 表示搜 `text_vector_index`
  - `image` 表示搜 `image_vector_index`

## 9. 当前新的 rerank 实验脚本

为了验证“大模型增强前的重排序效果”，当前新增了一份图文统一 PPR rerank 脚本：

- [`rerank_multimodal_ppr.py`](/mnt/data_1/yds/多模态/核心代码梳理/rerank_multimodal_ppr.py)

这份脚本当前采用的固定方案是：

- 文本候选：`dense_top20`
- 图片候选：`top20_image_hits`
- 编码模型：`Qwen3-VL-Embedding-2B`
- 查询初始化分数：只用 `query-candidate` 相似度归一化，不融合第一阶段分数
- 图结构：`candidate-candidate` 相似度 + 严格图文对边
- 严格图文对边定义：
  - 若文本候选 `text` 与图片候选 `content` 规范化后完全一致，则认为图文对齐
  - 若不一致，则不加 pair edge
- PPR 参数：
  - `alpha = 0.7`
  - `ppr_iters = 10`
- 去冗余选择：
  - `select_k = 3`
  - `redundancy_weight = 0.3`
  - `pair_complete_bonus = 0.1`
  - `min_gain = 0.05`

当前默认输入：

- 文本检索结果：
  - `/mnt/data_10/mwx/workspace/multi_modal_rag/draft/database_analysis/database_analysis/endobench_text_to_text_hybrid_recall_breakdown.jsonl`
- 图片检索结果：
  - `/mnt/data_10/mwx/workspace/multi_modal_rag/draft/database_analysis/database_analysis/endobench_image_to_image_recall_breakdown.jsonl`

当前默认输出：

- `/mnt/data_1/yds/多模态/核心代码梳理/output/endobench_multimodal_ppr_top3.jsonl`

这个输出已经对齐下游评测脚本要求：

- [`evaluate_from_retrieval_jsonl.py`](/mnt/data_10/mwx/workspace/multi_modal_rag/evaluate_benchmark/rag_generation_eval/evaluate_from_retrieval_jsonl.py)

额外说明：

- 图片侧直接使用 recall 文件自带的 `sample_id / group_id / image_path / content`
- 当前 `Qwen3-VL-Embedding-2B` 本地部署目录设定为：
  - `/mnt/data_1/yds/models/Qwen/Qwen3-VL-Embedding-2B`
- 当前已确认：
  - 图片候选和“配对描述文本”本身是有严格对齐逻辑的
  - 但 `dense_top20` 召回文本来自另一套文本检索链路
  - 因此在 rerank 里，不能直接依赖历史 `group_id` 去桥接图片与 `dense_top20`
  - 当前采用的 pair edge 规则是“文本完全一致才连边”，这会比较稀疏，但符合当前数据现实

因此支持：

- 图片向量 -> 原图：通过 `image_path`
- 图片向量 -> 文本：通过 `parent_sample_id -> sample_id`
- 文本向量 -> 图片：通过 `image_ids -> image_id`
